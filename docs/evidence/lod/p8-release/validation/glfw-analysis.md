The retained failed JVM report was symbolicated against its exact local `libglfw.dylib` (3.4.1-snapshot/arm64). The fault is a load from a null first argument plus offset 0x100, immediately before `CGDisplayCopyDisplayMode`. The caller obtains that argument from its window monitor field. This establishes a null monitor in the Cocoa video-mode path, rather than a MetalCraft resource pointer.

The instruction sequence matches GLFW's Cocoa monitor acquisition path, which obtains the monitor through the window and reads its display ID. [GLFW Cocoa window source](https://github.com/glfw/glfw/blob/master/src/cocoa_window.m), [GLFW Cocoa monitor source](https://github.com/glfw/glfw/blob/master/src/cocoa_monitor.m). The current source is corroborating structure, not a claim of byte-identical source provenance for the installed snapshot.

The stored stack places this during Fabric final window-size reset after the world is closed. Loss/reentrancy of monitor state during a Cocoa transition is a hypothesis; the report does not establish which callback cleared it. No renderer workaround is justified without reproducing that transition.
